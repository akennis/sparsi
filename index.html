Go Framework

AI Workflows,
Deterministic by Design

sparsi-go builds DAG workflows where deterministic code is the default. AI runs only where no deterministic solution exists — giving you predictability, auditability, and dramatically lower token costs.

Get Started View on GitHub For Leaders →

"Most AI workflows treat every step as a prompt. sparsi-go inverts this: determinism is the goal, and AI fills only the gaps the library cannot cover."

Why sparsi-go

Build AI workflows you can
test, audit, and trust

Every workflow decision is explicit. Every deterministic step is reproducible. AI only runs where it genuinely adds value.

🔒

Deterministic by Default

Library ops are pure functions. The same inputs always produce the same outputs — forever. Unit-test them without API keys. Cache their results. Compose them freely.

🤖

AI Only Where Needed

AI ops fire only when no deterministic solution covers the gap. Every AI call is logged with its exact input, output, and reasoning — fully inspectable after the fact.

⚡

Parallel by Architecture

The dagor engine resolves dependencies and schedules independent branches concurrently. No manual thread management — parallel execution comes free from the DAG structure.

🔍

Fail-Fast Isolation

When something goes wrong, the exact failing vertex is identified immediately. Errors don't cascade invisibly through a prompt chain — they surface at the source.

💰

Predictable Token Cost

AI call count is bounded by workflow structure, not by input length or model whims. As your op library grows, coverage expands and AI calls shrink.

🔀

Multi-Model by Design

Every AI op selects its own provider and model. Mix Claude and Gemini in one workflow — route verification to an independent model, send bulk ops to cheaper ones, and specialise by task without rewiring the graph.

The Decision Line

What belongs in code — and what belongs in AI

The boundary is sharper than it looks. Most "complex" workflow steps are actually deterministic once you know the rule. Reserve AI for what genuinely requires language understanding or judgment.

det op

Write Go code for this

Conditional routing

Once AI returns a category, all downstream if category == "billing" branching is a predicate gate — pure Go, zero tokens.

Formula scoring

Once AI extracts counts and durations, the difficulty formula ingredients + steps×1.5 + minutes×0.1 and band thresholds (easy/medium/hard) are all deterministic.

Structured text parsing

RegexExtractOp handles log lines, ISO dates, serial numbers, and any format you can describe as a pattern. No AI needed.

Lookup with fallback

StringLookupOp checks a map and returns "" on a miss. Wire that empty string into SkipIf on an AI op — AI only fires when the lookup fails.

API responses & JSON

HTTPGetOp + JSONExtractOp retrieves and parses structured API data deterministically. AI is only needed if the response is unstructured prose.

Arithmetic on extracted values

AddFloatOp/AddIntOp, MulFloatOp/MulIntOp, ClampFloatOp, RoundOp — once AI gives you numbers, all maths is deterministic. Separate float64 and int variants keep wires type-safe.

Threshold flags

"wet = precip > 0.1 mm", "windy = wind > 25 km/h" — float comparison predicates, not AI questions. The numbers are facts; the thresholds are your policy.

AI op

Use an AI op for this

Free-form classification

Categorising a support ticket as billing/bug/feature requires language understanding. Keyword matching misfires on edge cases; AI handles nuance reliably.

Extraction from unstructured prose

Pulling "name", "account_id", and "refund amount" from a customer's freehand email cannot be done with a fixed regex — field positions and phrasing vary.

Subjective scoring

"How severe is this bug?" and "What is the business impact of this feature?" require judgment. A formula can't encode what "critical" means without human-quality reasoning.

Semantic yes/no

"Does this bug report indicate a regression?" cannot be answered by keyword presence — a user might say "this used to work last month" without using the word "regression".

Summarisation & text generation

Compressing a document to a single sentence, or writing a context-aware outfit recommendation, requires understanding and generation — not a formula.

Semantic matching & ranking

"Which of these candidates is most relevant to the query?" requires understanding both the query and the candidates — not a string-equality or cosine-similarity shortcut.

Open-ended number parsing

Converting "$1.2k", "two thousand", or "approx. 40–50" to a canonical float cannot be done reliably with a regex when user phrasing is unconstrained.

💡

The practical test: if you could write a unit test that passes reliably without calling an LLM, it belongs in a deterministic op. If the answer depends on reading a sentence and understanding what a human likely meant — it belongs in an AI op.

Library Reference

Pre-built AI ops

Drop-in AI ops for the most common workflow needs. Each one is a typed Go struct with a single AI call and retry-on-parse-failure. Reasoning is captured via WithReasoningLog when needed. Token costs are approximate and scale with input length.

Op What it does Output type Typical tokens (in / out)
ModeSelectOp Classifies text into exactly one of N caller-specified categories. Use it at the top of a multi-branch workflow to dispatch to the correct lane. string (one category) 200 + input / ~5
AIClassifyMultiLabelOp Tags text with zero or more of N categories. Use when a document can legitimately belong to multiple buckets simultaneously. []string 200 + input / ~20
AIBoolOp Answers a yes/no predicate about the input — e.g. "does this contain PII?", "is this a regression?". The tightest possible AI call: output budget is 8 tokens. bool 150 + input / ~2
AIScoreOp Scores text against a caller-defined criterion and returns a float64 in [0, 1]. Examples: relevance, severity, readability, toxicity. Output budget: 16 tokens. float64 ∈ [0,1] 200 + input / ~3
AIParseNumberOp Converts free-form text to a float64: handles "$1.2k", "two thousand", "approx. 40–50", currency symbols, and written-out numbers. Use after any unstructured numeric field. float64 200 + input / ~5
AIExtractStringSliceOp Pulls a list of items from prose — ingredients from a recipe, steps from instructions, names from a paragraph. Returns a []string (CSV-serialised internally). []string 200 + input / ~50
AIExtractMapOp Extracts a fixed set of named fields from free text — name, email, account ID, amounts — when the fields are known but their position and phrasing vary per document. map[string]string 200 + input / ~80
AISummarizeOp Distils a []string of items into a single summary string. The operation param shapes the instruction — "one concise sentence", "bullet-point highlights", etc. string 200 + items / ~150
AIComputeStringToStringOp General text-in, text-out transformation: summarise, translate, rewrite, generate a recommendation. The broadest AI op — use it when none of the narrower ops fit. string 200 + input / 50–500
AIBestMatchOp Given a query and a list of candidates, returns the 0-based index of the single best match. Use for semantic routing, FAQ lookup, or product recommendation. int (index) 200 + query + candidates / ~3
AIRerankOp Reranks a list of candidates by relevance to a query, returning a full permutation of 0-based indices (best first). Use when order matters, not just the top pick. []int (permutation) 200 + query + N×candidates / ~N×3
AIComputeMathOperandsToFloat64Op Performs any binary float64 operation that doesn't exist in the deterministic library — e.g. geometric mean, weighted harmonic average, or domain-specific formulas. The canonical AI-as-fallback example. float64 ~150 / ~5

All built-in ops default to claude-sonnet-4-6, but every op accepts provider and model parameters — assign any model to any vertex, mix Claude and Gemini in one workflow. Token counts are input-text-dependent; "input" means prompt overhead beyond the content you supply. Every op retries up to 3× on parse failure with configurable exponential back-off.

Multi-Model Orchestration

The right model for every step —
in a single workflow

Every AI op carries its own provider and model parameters. Mix Claude and Gemini within one DAG, route tasks to the model best suited for them, and use a second independent model to verify the first. OpenAI support is on the roadmap.

🔍

Independent Verification

A model that generated content has already committed to its framing — it tends to see what it expects. Wire a second, independent model as a quality gate: it surfaces unsupported claims the first model overlooked. The faithful-summary example has Claude summarise, then Gemini verify that every factual claim is grounded in the source.

⚡

Cost-Optimized Routing

Not every op needs your most capable model. Route bulk boolean checks and simple classification to a cost-efficient model; send complex reasoning, long-context synthesis, or code generation to your highest-tier model. Cost per run drops without touching any business logic.

🎯

Specialization by Task

Different providers lead on different capabilities. Use the model with the best multilingual support for localisation ops, the strongest code model for generation steps, the fastest model for high-throughput boolean checks — all composable within one coherent workflow.

Model selection is per-vertex, not per-workflow

The provider and model params live on each op independently. Changing any op to a different model is a one-line edit — the rest of the graph is untouched. Exponential back-off retry is also parameterised per op, so high-value ops can retry more aggressively than cheap bulk calls.

  • Claude (Anthropic) — supported today
  • Gemini (Google) — supported today
  • OpenAI — on the roadmap
  • Custom providers — any Go struct that calls your endpoint
See the faithful-summary example →
faithful-summary / main.go 
// Claude generates the summary
Vertex("summarize").Op("AIComputeStringToStringOp").
    Params(map[string]string{
        "operation": "summarize in 3–5 concise sentences…",
        "provider":  "claude",
        "model":     "claude-sonnet-4-6",
    }).
    Input("Input", "source").
    Output("Result", "summary").

// Gemini independently checks faithfulness
Vertex("verify").Op("AIBoolOp").
    Params(map[string]string{
        "predicate": "does every factual claim appear in the source?",
        "provider":  "gemini",
        "model":     "gemini-3-flash-preview",
    }).
    Input("Input", "query").
    Output("Result", "faithful")

Two different providers, one workflow. The deterministic formatting op in between assembles the verification prompt — zero tokens, zero latency.

Comparison

sparsi-go vs. a pure LLM chain

When every step is a prompt, every step pays the cost of non-determinism.

Dimension ⚡ sparsi-go Pure LLM Chain
Output reproducibility ✓ Deterministic steps always reproduce exactly ✗ Non-deterministic at every link
Token cost ✓ Tokens only for true AI gaps; all else is free ✗ Every transformation burns tokens
Unit testability ✓ Deterministic ops tested without any API key ✗ No natural isolation boundary for testing
Failure attribution ✓ Error pinpointed to the exact failing vertex ✗ Error buried somewhere in the chain
Audit trail ✓ Every AI call logs input, output, reasoning ✗ Black box; no per-step record
Parallel execution ✓ Independent branches run concurrently for free ✗ Sequential by default; parallelism is manual
Model-version stability ✓ Deterministic logic is immune to model drift ✗ Behaviour shifts when the provider updates
Conditional branching ✓ Predicate gates prune skip-propagated subtrees ✗ Requires a meta-prompt or glue code
Compliance readiness ✓ Deterministic steps satisfy data-flow requirements ✗ Hard to prove consistency run-to-run
How It Works

Three layers, one coherent workflow

1

Define Your DAG

Wire deterministic library ops for every step where the logic is known. Annotate struct fields with dag:"input" / dag:"output" tags and connect them with a fluent builder.

2

AI Fills the Gaps

Where no deterministic op covers the need, drop in an AIComputeOp, ModeSelectOp, or any typed AI op. Use SkipIf wires so AI only fires on cache misses.

3

Run With Confidence

The dagor engine resolves dependencies, executes independent branches in parallel, and surfaces failures with vertex-level precision. Ship it as a CLI or MCP server.
