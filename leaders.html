AI That Your Auditors
Can Inspect

AI workflows built on prompt chains are opaque by construction. sparsi-go inverts that: logic is in code, AI is a controlled component, and every decision is traceable back to the vertex that made it.

The Business Case

Three things that change when you
adopt sparsi-go

01 — Control

Your logic stays in your code

In a pure LLM chain, business logic migrates into prompt text — brittle, hard to version, sensitive to model updates. In sparsi-go, logic is Go code. Deterministic ops are plain structs with a Run method. Reviewable, diffable, deployable like any other software.

AI is a narrow, explicitly-bounded component. You decide which vertices call the model. You decide what prompt they use. You decide which output wire carries the result. The model cannot exceed the scope its vertex defines.

  • Workflow structure is static and code-reviewable
  • Changing a prompt is a commit, not tribal knowledge
  • Conditional branches are Go predicates, not meta-prompts
  • AI surface area is explicit and bounded

Where does the logic live?

Pure LLM chain

"You are a support agent. First classify the ticket.
Then, if billing, extract the following fields…
If a bug, list reproduction steps and score severity…
Remember to also check for regressions. Return JSON.
// business logic buried in prompt text"

sparsi-go

// classify — one AI call, typed output
Op("ModeSelectOp").Condition(…)
// route — pure Go predicate
Vertex("gate_bug").Condition("lane_is_bug")
// extract — scoped AI op
Op("AIExtractStringSliceOp")
02 — Cost

AI costs are bounded
by structure

In a prompt chain, costs scale with the length of the conversation and the complexity of the prompt. One long "do everything" prompt is expensive every single call.

In sparsi-go, each AI op is narrow and typed. A classification call is one sentence in, one category out. An extraction call sends exactly the relevant body, not the entire conversation context. Conditional gates ensure AI ops in unused branches are never called at all.

  • AI call count is bounded by the workflow graph
  • Unused conditional branches burn zero tokens
  • SkipIf wires add a free deterministic cache layer
  • As the op library grows, AI calls naturally shrink
  • No per-run "surprise" costs from prompt bleed

Token consumption per run (ticket triager example)

Pure LLM chain ~2,400 tokens / call
Full context every step + routing meta-prompt
sparsi-go (billing ticket) ~380 tokens / call
classify + 2 billing AI ops only

Unused lanes (bug / feature / other) are pruned by the engine — those AI ops are never invoked.

03 — Compliance & Auditability

Every decision is traceable

Regulators and auditors want to know: given this input, how did the system reach this output? In a prompt chain, the answer is "the model decided" — an answer that satisfies almost no one.

In sparsi-go, every run produces a trace. Deterministic ops have known, reproducible behaviour. AI ops log their exact prompt, model response, and reasoning string. The DAG topology itself is a static artefact you can commit, review, and version.

  • Deterministic steps satisfy data-flow audit requirements
  • AI ops log input + output + reasoning on every call
  • Workflow structure is code — version-controlled and reviewable
  • Run-level ai_nodes field records exactly which AI ops fired
  • Model name and version are explicit in op configuration

Run output includes full provenance

run output (JSON) 
{
  "category": "billing",
  "details": { /* extracted fields */ },
  "ai_nodes": [
    "ModeSelectOp",           // classified
    "AIExtractMapOp(billing)", // extracted
    "AIParseNumberOp(refund)"  // parsed
  ]
  // + per-op: input, output, reasoning
}

Every AI call is attributed to a named vertex with a typed signature. No reasoning happens outside the declared graph.

Risk Analysis

How sparsi-go changes your risk profile

Every risk category that matters to engineering leaders, compared directly.

Pure LLM chain

Unpredictable outputs

The same input produces different outputs on re-run. Any downstream system depending on the response must tolerate undefined variability.

sparsi-go

Deterministic where it matters

Pure-function ops produce identical outputs on identical inputs. Only AI ops introduce variance — and their scope is explicitly bounded.

Pure LLM chain

Model version sensitivity

When the provider updates the model, prompt behaviour changes silently. You discover this in production, not in code review.

sparsi-go

Model changes are contained

Deterministic logic is immune to model changes. Only AI ops are affected — and they're explicitly declared, so the blast radius is known before the update lands.

Pure LLM chain

Runaway token costs

Each step passes accumulated context. A complex workflow with ten steps multiplies token usage linearly. Cost spikes are hard to attribute to a specific step.

sparsi-go

Bounded, attributable costs

Each AI op sends only the data its vertex declares. Cost per run is the sum of declared AI ops that actually fire — zero surprises, easy chargebacks.

Pure LLM chain

Silent reasoning failures

When the chain produces a wrong answer, debugging requires replaying multi-step conversations and guessing which link failed.

sparsi-go

Vertex-level failure isolation

Errors surface at the exact vertex that failed. The engine attributes the failure before any downstream steps run. MTTR drops dramatically.

Pure LLM chain

Vendor lock-in via prompt engineering

Complex, model-specific prompt engineering accumulates over time. Migrating to a different provider means rewriting invisible business logic.

sparsi-go

Logic lives in code, not prompts

Business rules are Go code — portable and provider-agnostic. AI ops accept provider and model parameters: redirect any op to a different provider in one line, or mix Claude and Gemini within a single workflow. BSD 3-Clause licensed.

Pure LLM chain

Confirmation bias compounds across steps

A model asked to verify its own output shares the same priors and blindspots that produced it. Hallucinations go unchallenged — the verifier sees what it expects to see.

sparsi-go

Independent model as quality gate

Route verification to a different provider. A Gemini check on Claude-generated content — or vice versa — surfaces unsupported claims that either model alone would rationalise away. Model selection is a per-vertex parameter, not a global setting.

Team Readiness

How to prepare your team

sparsi-go introduces one new pattern. Your team likely knows everything else already.

Phase 1 — Day 1–5

Learn the Op Pattern

  • An op is a Go struct with dag:"input" / dag:"output" tags and a Run(ctx) method
  • Think of each op as a pure function: inputs → outputs, no side-effects
  • The daggen tool generates boilerplate from struct tags
  • Run the existing examples with a CLAUDE_API_KEY
Phase 2 — Week 1–2

Design DAGs Before Writing Code

  • Draw the workflow as a graph before touching keyboard
  • For each node: is this deterministic or does it need AI judgment?
  • Identify where conditional routing is needed (predicate gates)
  • Name wires explicitly — they document the data flow
Phase 3 — Week 2+

Build and Grow the Library

  • Every reusable deterministic op added to the library reduces future AI calls
  • Start AI ops broad; narrow them as you learn what can be made deterministic
  • Add SkipIf wires where you can cache or lookup first
  • Monitor ai_nodes output to track AI call counts per workflow

FAQ

Common questions from leadership

Does adopting sparsi-go require a full rewrite?
No. sparsi-go is a Go library. You can introduce it incrementally — start with one new workflow, prove the pattern, then expand. Existing services don't need to change.
Which AI providers are supported?
The built-in library ops support Claude (Anthropic) and Gemini (Google) today, with OpenAI on the roadmap. Every AI op accepts provider and model parameters — switch any op to a different provider in one line, mix models within a single workflow, and use an independent second model as a verification gate. The deterministic ops have no provider dependency whatsoever.
How are API keys managed in production?
sparsi-go exposes an AIClientFactory interface (analogously for embeddings, EmbeddingClientFactory) — implement it once to source credentials from HashiCorp Vault, AWS Secrets Manager, workload identity, an egress proxy, or per-tenant credential stores. The bundled env-var factory is for laptops and CI; production deployments register their own. Graph code is unchanged. See the credential-routing guide.
Can workflows call external tools — browsers, search APIs, internal services?
Yes, via Model Context Protocol. MCPCallOp handles one-shot tool calls against either a local subprocess (over stdio) or a remote server (streamable HTTP). MCPScriptOp orchestrates multi-call sessions that share server state — a single browser instance navigating, typing, and snapshotting in one DAG step. A warm-replenish pool keeps cold-start off the critical path on fan-out. See the MCP guide.
How does retrieval-augmented generation work, and how do you prevent hallucinated citations?
Implement library.Retriever for any backend (BM25, vector store, hosted search) and wire RetrieveOp into the graph. The library also ships a deterministic ValidateCitationsOp that filters LLM-emitted source names against the allow-list of identifiers actually retrieved on that request — hallucinated citations are partitioned out and surfaced via slog at WARN. Built-in audit boundary. See the retrieval guide.
How does this compare to LangChain or other orchestration frameworks?
LangChain and similar frameworks make it easy to chain prompts. sparsi-go makes it possible to not chain prompts — using deterministic Go code for everything that doesn't need AI, and explicit typed ops for everything that does. The result is leaner, cheaper, and debuggable.
What if our use case genuinely needs AI at every step?
sparsi-go supports that too — every vertex can be an AI op. But in practice, most workflows have at least some steps that are pure transformation: parsing, routing, scoring, filtering. Even replacing 30% of AI calls with deterministic ops has meaningful cost and reliability impact.
How do we handle the generated MCPB packages?
When the codegen driver compiles a workflow successfully, it packages the binary and a manifest.json into a .mcpb archive (a ZIP). This can be deployed to any server or MCP-compatible client. No runtime beyond the binary itself is required.
What is the migration path if we later want to remove an AI op?
Replace the AI op vertex with a deterministic op of the same input/output types. Wire names stay the same. The rest of the graph is untouched. This is the natural evolution path as your op library matures — AI ops are intended to shrink over time, not grow.
