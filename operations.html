DevOps

Deploy Anywhere.
One Binary. No Dependencies.

sparsi-go workflows compile to a single static Go binary with no external runtime dependencies — no shared libraries, no interpreter, no container required. Drop the binary on any machine and it runs.

Standalone Binaries ↓ Context Timeouts ↓ Logging & Metrics ↓
Default Deployment

Standalone Executables

The code-generation driver produces a complete, runnable Go program. go build it and you get a single self-contained binary.

terminal 
# Build — produces a single binary, nothing else
go build -o ticket-triager ./examples/ticket-triager

# Run — feed JSON on stdin, result on stdout
echo '{"body":"My payment failed twice"}' \
  | ./ticket-triager

# Errors and diagnostics go to stderr
./ticket-triager < ticket.json > brief.json

What "no external dependencies" means

Go compiles everything — the standard library, the dagor runtime, the operator logic, and all third-party packages — directly into the binary. The resulting executable has:

  • No .dll or .lib files on Windows
  • No .so shared objects on Linux
  • No .dylib files on macOS
  • No language runtime to install (no JVM, no Python interpreter)
  • No node_modules, no pip install, no gem install

The only exception is when an operator uses CGo (e.g. SQLite via mattn/go-sqlite3). The built-in and generated operators are pure Go and introduce no such dependency.

The stdin / stdout / stderr contract

stdin

Raw input — ticket text, a JSON document, a batch of records. The first operator reads and parses it. No file path arguments needed; works naturally with Unix pipes.

stdout

The workflow result — structured JSON, a plain-text report, or any typed output your last operator writes. Downstream programs can parse it directly.

stderr

Operator logs, the SlogReporter stream, and any fatal error messages. Separate from the result so logging never corrupts the structured output.

Deployment scenarios

Cron / Batch job

Schedule the binary with cron, Task Scheduler, or a Kubernetes CronJob. One invocation = one workflow run. No server process to keep alive.

crontab 
0 * * * * /opt/bin/analyzer < /data/input.json \
              >> /logs/output.ndjson 2>>/logs/err.log

AWS Lambda / Cloud Functions

Compile for GOOS=linux GOARCH=amd64, zip, upload. The handler reads the event payload, runs the graph, returns the result. Cold starts are fast — small binary, no interpreter warmup.

terminal 
GOOS=linux GOARCH=amd64 go build -o bootstrap .
zip function.zip bootstrap

Container (Docker / Kubernetes)

The binary is the only artifact the container needs. Use a scratch or distroless base image for minimal attack surface. No OS packages, no language runtime layer.

Dockerfile 
FROM golang:1.23 AS build
WORKDIR /src
COPY . .
RUN CGO_ENABLED=0 go build -o /app .

FROM scratch
COPY --from=build /app /app
ENTRYPOINT ["/app"]

Unix pipeline stage

Chain multiple workflow binaries together. Each step reads structured output from the previous. Compose complex multi-model pipelines out of single-purpose binaries without modifying any code.

terminal 
cat tickets.ndjson \
  | ./triage \
  | ./enrich \
  | ./route > routed.ndjson
Confirmed in dagor

Context Timeouts

The dagor engine fully honours Go's context.Context cancellation and deadline semantics. Pass a context with a timeout or deadline to engine.Run(ctx) and the engine will stop cleanly if that deadline is exceeded.

How timeouts propagate

Context cancellation is checked at every level of the execution stack:

  • Graph level — engine.Run selects on ctx.Done() alongside the normal completion signal. Whichever fires first wins.
  • Vertex level — each vertex checks ctx.Err() before executing, returning early if the context is already cancelled.
  • Operator level — the context is forwarded into every op.Run(ctx) call; operators that make network calls (e.g. AI ops) respect it natively.
  • Map / Filter / Reduce — each element iteration checks ctx.Err() before processing the next item, so a timeout mid-loop exits cleanly.

After cancellation, the engine waits for all active goroutines to finish their current vertex before returning — it does not kill goroutines. The error returned by engine.Run will be context.DeadlineExceeded or context.Canceled.

main.go 
import (
    "context"
    "time"
    "github.com/wwz16/dagor"
)

// Hard deadline: abort entire workflow after 5 s.
ctx, cancel := context.WithTimeout(
    context.Background(), 5*time.Second,
)
defer cancel()

eng, _ := dagor.NewEngine(graph, pool)
defer eng.Close(ctx)

if err := eng.Run(ctx); err != nil {
    if errors.Is(err, context.DeadlineExceeded) {
        // Workflow took too long — return a partial result
        // or a 504 to the caller.
    }
    return err
}

Timeout patterns

Per-request deadline

Derive the context from the incoming HTTP request. If the client disconnects or times out, the graph stops automatically — no goroutine leak, no wasted AI tokens.

handler.go 
func handler(w http.ResponseWriter, r *http.Request) {
    ctx, cancel := context.WithTimeout(
        r.Context(), 10*time.Second,
    )
    defer cancel()
    eng.Run(ctx)
}

Global process budget

In a batch or CLI program, set a single timeout for the whole run. The engine will drain whatever it can within the window and return a clear error if time runs out.

main.go 
ctx, cancel := context.WithTimeout(
    context.Background(),
    30*time.Second,
)
defer cancel()
eng.Run(ctx)

Graceful shutdown

Hook OS signals into a cancel function. When SIGTERM arrives the engine finishes in-flight vertices and returns, letting the process exit cleanly without a hard kill.

main.go 
ctx, stop := signal.NotifyContext(
    context.Background(),
    syscall.SIGTERM, syscall.SIGINT,
)
defer stop()
eng.Run(ctx)

Because engine.Run passes the context directly into every op.Run(ctx) call, AI operators that use the Claude SDK or any other HTTP client will honour the deadline without any special wiring — the SDK's HTTP transport propagates it automatically.

Advanced

Web Service Integration

A dagor graph can be called from inside any HTTP handler, gRPC method, or message-queue consumer. The engine is not a server — it is a function call that happens to be graph-shaped. Embed it wherever you call functions.

Per-request pattern (simple)

Build a new engine instance for every request. This is the simplest and safest approach: engines are lightweight, state is never shared between requests, and the request context controls the lifetime.

server.go 
// Build the graph once at startup (it is immutable).
var triageGraph *graph.Graph

func init() {
    triageGraph, _ = dagor.NewGraphFromJson(graphJSON)
}

func triageHandler(w http.ResponseWriter, r *http.Request) {
    ctx, cancel := context.WithTimeout(r.Context(), 10*time.Second)
    defer cancel()

    eng, err := dagor.NewEngine(triageGraph, goroutinePool)
    if err != nil {
        http.Error(w, err.Error(), http.StatusInternalServerError)
        return
    }
    defer eng.Close(ctx)

    if err := eng.Run(ctx); err != nil {
        http.Error(w, err.Error(), http.StatusInternalServerError)
        return
    }

    result, _ := eng.GetOutput("final_brief")
    json.NewEncoder(w).Encode(result)
}

What gets shared vs. per-request

Share across requests

  • *graph.Graph — immutable after build
  • Goroutine pool (ants.Pool or equivalent)
  • Operator registrations (init()-time, global)

Create per-request

  • *dagor.Engine — holds mutable run state
  • Context (carries deadline + run ID)
  • Input wires (injected before Run)

The goroutine pool is shared intentionally: it bounds total concurrency across all in-flight requests, preventing a traffic spike from spawning unbounded goroutines.

Goroutine pool sizing

The pool controls how many vertices run in parallel across all concurrent workflow executions. A reasonable starting point is 2–4× the number of CPU cores for CPU-bound graphs. For IO-heavy graphs (many AI ops), go higher — goroutines waiting on network are not consuming CPU.

main.go 
import "github.com/panjf2000/ants/v2"

// For AI-heavy workflows: most goroutines are waiting on HTTP.
// A large pool lets more requests make progress concurrently.
pool, err := ants.NewPool(200,
    ants.WithNonblocking(false), // block callers when full
    ants.WithPreAlloc(true),    // allocate goroutines eagerly
)
defer pool.Release()
Built-in

Logging & Metrics

dagor ships a Reporter interface that fires structured events throughout the graph lifecycle. The built-in SlogReporter routes every event to Go's standard log/slog logger — including per-vertex durations and, for AI ops, exact token counts after every LLM call.

Wiring up the SlogReporter

Pass any *slog.Logger to reporter.New and supply it as an engine option. Every event automatically includes the workflow's run_id so concurrent runs can be correlated in any structured log sink.

main.go 
import (
    "log/slog"
    "os"
    "github.com/wwz16/dagor/reporter"
)

// JSON output to stderr — works with any log aggregator.
logger := slog.New(slog.NewJSONHandler(os.Stderr, &slog.HandlerOptions{
    Level: slog.LevelDebug, // Info = graph + AI tokens; Debug adds per-vertex
}))

eng, _ := dagor.NewEngine(graph, pool,
    dagor.WithReporter(reporter.New(logger)),
)
eng.Run(ctx)

Events emitted

Info level

  • graph.start — graph name, run_id
  • graph.finish — graph, run_id, dur_ms (err on failure)
  • <AIop>.tokens — input_tokens, output_tokens, run_id

Debug level

  • vertex.start — graph, vertex, type, run_id
  • vertex.finish — graph, vertex, type, dur_ms, run_id
  • vertex.skipped — graph, vertex, reason, run_id
  • vertex.fields — vertex inputs and outputs by phase

AI Token Logging

Every AI operator in sparsi-go/library (AIClassifyMultiLabelOp, AIScoreOp, AIBoolOp, AIBestMatchOp, AIRerankOp) logs input_tokens and output_tokens at Info level after each LLM call. No extra wiring — tokens appear automatically whenever a logger is attached to the engine.

stderr — JSON log lines 
{"level":"INFO","msg":"graph.start",
  "run_id":"3f9a2c…","graph":"ticket-triage"}
{"level":"INFO","msg":"AIClassifyMultiLabelOp.tokens",
  "run_id":"3f9a2c…","input_tokens":312,"output_tokens":18}
{"level":"INFO","msg":"AIBoolOp.tokens",
  "run_id":"3f9a2c…","input_tokens":84,"output_tokens":6}
{"level":"INFO","msg":"graph.finish",
  "run_id":"3f9a2c…","graph":"ticket-triage","dur_ms":1240}

Aggregating token costs

Because every token event carries a run_id, you can sum costs per workflow run with any JSON log tool — no tracing SDK required.

terminal — jq 
# Total tokens consumed by one run
grep '"run_id":"3f9a2c"' app.log \
  | jq -s '[.[] | select(.input_tokens)
           | (.input_tokens + .output_tokens)] | add'

# Per-run token totals across all runs
jq -s 'group_by(.run_id)[] | {
  run_id: .[0].run_id,
  tokens: ([.[].input_tokens, .[].output_tokens]
           | map(numbers) | add)
}' app.log

Set the handler level to slog.LevelInfo in production to suppress per-vertex debug chatter while keeping graph timings and token costs visible.

Reasoning Log

By default, AI ops produce only their typed result — the model's chain-of-thought is discarded. Opt in to reasoning capture by deriving a context with library.WithReasoningLog and passing it to eng.Run. Every AI op executed inside that run appends a ReasoningEntry to the log; read the entries after the run with no further wiring.

Each entry records the op name, the dagor run_id, a snapshot of input field values, the output value, and the full reasoning string. The log is safe for concurrent use across parallel graph vertices.

Field Type Contents
Op string Op type name, e.g. "AIScoreOp"
RunID string dagor workflow run ID for cross-referencing logs
Inputs map[string]any Snapshot of the op's input fields at invocation time
Output any The value produced by the op (e.g. float64, bool, []string)
Reasoning string Model's chain-of-thought for this invocation

When reasoning is disabled (the default), AI ops skip the reasoning request entirely. There is no performance cost for runs that do not opt in.

Enabling reasoning and dumping entries

main.go 
import (
    "encoding/json"
    "os"
    "github.com/akennis/sparsi-go/library"
)

// Derive a context that collects reasoning.
ctx, reasonLog := library.WithReasoningLog(context.Background())

// Run the graph — all AI ops inside record their reasoning.
if err := eng.Run(ctx); err != nil {
    log.Fatalf("run: %v", err)
}

// Read entries after the run — no context lookup needed.
enc := json.NewEncoder(os.Stdout)
enc.SetIndent("", "  ")
for _, e := range reasonLog.Entries() {
    enc.Encode(e)
}

Each entry is emitted as a JSON object on stdout:

stdout — one JSON object per AI op 
{
  "Op": "AIScoreOp",
  "RunID": "3f9a2c…",
  "Inputs": {
    "Input": "This blender is okay but a bit loud.",
    "Criterion": "customer satisfaction"
  },
  "Output": 0.42,
  "Reasoning": "The review is mildly negative about noise but
not strongly dissatisfied. Score reflects lukewarm sentiment."
}
{
  "Op": "AIBoolOp",
  "RunID": "3f9a2c…",
  "Inputs": { "Input": "This blender is okay but a bit loud." },
  "Output": false,
  "Reasoning": "No spam, abuse, or policy violation detected."
}

The Reporter interface is open: implement OnGraphFinish to push a latency histogram to Prometheus, or wrap SlogReporter to also emit OpenTelemetry spans. The built-in reporter is the zero-config starting point — replace or compose it for production observability stacks.

AI credential routing

Where API keys actually come from

Every AI op resolves its provider SDK client through an AIClientFactory. The bundled factory reads CLAUDE_API_KEY / GEMINI_API_KEY from the environment — fine for laptops and CI. In production, register your own factory to source credentials from Vault, AWS Secrets Manager, workload identity, an egress proxy, or per-tenant vaults — without touching graph code.

①

Process-wide default

Replace once at main() startup. Every AI op picks it up.

library.SetDefaultAIClientFactory(vaultFactory)
②

Registered by id

Register multiple factories. Each vertex selects one via client_factory_id.

library.RegisterAIClientFactory("prod", prod)
library.RegisterAIClientFactory("sandbox", sandbox)
③

Per-vertex ref

credential_ref routes inside the chosen factory — tenant id, environment, Vault path.

Params(map[string]string{
    "client_factory_id": "prod",
    "credential_ref":    "tenant-acme",
})

Security: the bundled factory's per-ref cache has no eviction. Never derive ref from per-request input (tenant id from a request header, user-supplied query parameter) — that produces an unbounded cache and a DoS vector. Use ref only for the small, named credential sets the application controls. See the credential-routing guide for the worked Vault example.

The EmbeddingClientFactory abstraction follows the same shape for retrievers that embed text — see the retrieval guide.

MCP pool sizing

Warm-replenish pools for fan-out

Stdio MCP servers carry a meaningful cold-start (Node.js boot, browser binary download, protocol handshake). A graph that fans MCPCallOp / MCPScriptOp across N items would otherwise pay that cost N times. Set pool_size on the vertex and the library maintains a target number of pre-started subprocesses; vertices sharing the same canonical session spec share warm slots.

pool_size

Target pool capacity per spec. 0 (default) disables pooling — every Run opens and closes its own session.

pool_prewarm

true (default) fills the pool during Setup so the first Run already has warm sessions. Set false for lazy fill.

Shutdown contract

Call library.ShutdownMCPPool(ctx) from main() — typically via defer — so pre-started subprocesses drain cleanly at exit. Without it, the runtime kills them on signal.

main.go — pooled fan-out 
shootParams := map[string]string{
    "command":   "npx",
    "args":      "-y,@playwright/mcp@latest",
    "out_dir":   outDir,
    "pool_size": "8", // 8 warm playwright-mcp subprocesses
}

func main() {
    // ...
    defer library.ShutdownMCPPool(context.Background())
    // engine.Run(ctx) ...
}

Each borrow is a fresh session — the pool never reuses a session for a second logical call. Pooling is supported only for transport="stdio" in v1. See the MCP integration guide for the full operator surface.
